# 《数智方舟》Live2D 模型自动化生成 —— 技术咨询文档

> 面向指导老师的阶段性技术报告。目标：说明项目背景、已完成部分、已探索的失败路径、当前核心困难，并请教方案。

---

## 一、项目背景与目标

**项目**：《数智方舟》——基于 ESP32-P4 的智能设备，设备上运行自研 Live2D 渲染引擎，角色以 Live2D 模型作为表情/语音交互形象。

**需求**：为明日方舟 300+ 干员提供 Live2D 模型。团队**没有专业绑骨美术**，源素材只有静态立绘 PSD（分层），因此必须建立一条**从静态立绘到 Live2D 模型的自动化流水线**。一人手动绑骨一个角色约需 1-2 天，300 角色不可行，自动化是硬需求。

---

## 二、已打通的链路（这部分已完成，不是问题）

```
分层 PSD（seethrough 分割：face/front hair/mouth/neck… 30+ 层）
  → 自动绑骨 → .cmo3（Cubism Editor 工程格式）
  → Cubism Editor 5.0 → 导出 .moc3（SDK 5.0，v4.2+ SectionOffsetTable 布局）
  → PC Demo（Cubism SDK 5.0 + 自研导出工具）→ model.l2d + keyforms.bin
  → tuner（PC 预览调参）
  → ESP32-P4 设备端自研渲染引擎（lv2_render，软光栅 RGBA8888 + Alpha 混合 + 遮罩裁剪 + Keyform 变形）
```

**已攻克的技术点**：
1. moc3 v5.0 二进制格式解析（48 子表 SectionOffsetTable）
2. P4 端纯软件 Live2D 渲染（无 GPU 依赖，实时 30fps）
3. cmo3 工程格式（CAFF 加密容器：XOR 混淆 + ZIP 压缩）的完整解密/修改/打包工具链
4. 设备端参数驱动（AngleX/Y/Z、EyeLOpen、MouthOpenY 等 11 参数动画）

**结论**：**模型文件 → 引擎渲染的全链路已跑通并验证多次**，问题的关键在"模型文件从哪来"。

## 三、探索过的自动绑骨路径与失败教训

### 3.1 方案 A：stretchystudio（自动绑骨工具，网页版）

开源项目 stretchystudio：输入分层 PSD，自动生成骨架 + Warp 变形器 + 参数绑定，输出 .cmo3。

**遇到的问题**：
1. **网页版与 GitHub master 代码分叉**：网页版（完整版，157 个 warp 变形器）未开源；master 是重构中的半成品（89 个 warp，Editor 打开人物消失）。**修复 master 不可行**（重构未完成，工程量不可控）。
2. **自动绑骨质量根因链**（已定位，修复困难）：
   ```
   seethrough 分割输出含散布全画布的噪声像素（1-2px 碎点）
     → 自动网格生成产生大量碎片顶点（嘴部 136 顶点中 99 个是碎片）
     → 碎片把图层 bbox 拉爆成全画布
     → 骨架启发式（facePivot 校准）落在画布外 (671, 1406.9)
     → 头部旋转中心错误 → 转动时头部整体平移/绕脚下旋转
   ```
3. **坐标系混乱**（当前最大障碍，详见第四节）

### 3.2 方案 B：脚本修补 cmo3 坐标（fixed2~fixed17 迭代）

针对 stretchystudio 输出做 XML 级后处理：FaceRotation 旋转中心改到下巴、脖子双层锁定、FaceParallax 位移场修正、嘴部 keyform 注入。

**结果**：**在 moc3→PC Demo→P4 设备链路上验证有效**，但在 **Cubism Editor 中打开渲染仍然错误**（头绕画布外远点旋转"掉到脚下"、头饰反向运动）。经 diff 验证（Editor 打开另存前后逐字节对比），Editor 并未重烘焙数据，即**脚本写入的坐标值与 Editor 渲染期望的坐标空间不一致**——同一份数据在 Editor 与导出链路中表现不同，导致修复无法在 Editor 中可视化验证，只能在设备端盲调。

### 3.3 方案 C：THA（LivePortrait 稠密运动场）驱动嘴部变形

利用快手 LivePortrait 的稠密运动场（dense motion field），输入"张嘴驱动帧"，提取嘴部区域的顶点位移，生成 Live2D 嘴部 keyform。

**实验结果（已完整验证）**：
1. 环境/权重/推理管线全部跑通（RTX 4060，3 秒/角色）
2. 跨身份张嘴驱动信号有效（absolute+lip_retargeting 模式，嘴部区域变化量 8 倍于默认模式）
3. **但稠密运动场（64×64 网格，8px/格）对动漫小嘴（15×5px）的开合分离被插值抹平**：嘴部四周位移全部为"整体 +25px 向下"（下巴下沉），上唇上移/下唇下移的分离信号为零（gap=0.0）。kp 隐式关键点同样无分离。
4. 结论：**神经网络运动场在此任务上不提供几何规则之外的额外价值，已止损**。唯一有效产物是 insightface landmark 的开合比例参数（上:下 ≈ 2:1）。

### 3.4 方案 D（进行中）：几何规则张嘴 + 程序化口腔

1. **张嘴 keyform**：以嘴中线为轴，上唇上移/下唇下移/嘴角内收的抛物线权重变形，幅度/比例为可调参数。已注入 cmo3 并验证文件结构正确（Editor 保存后数据原样保留）。
2. **程序化口腔模板**：深色口腔底 + 双排牙齿 + 舌头，按嘴部 bbox 参数化矢量生成，作为 mouth inside ArtMesh 写入纹理图集。
3. **并行**：一位同学正在手动绑骨一个标准角色作为模板工程，用于骨架结构/嘴部结构参照。

## 四、当前核心困难（请教重点）

### 困难 1：自动绑骨的坐标系一致性（最根本）

**现象**：stretchystudio 导出的 cmo3 中，同一模型内数据处于**不同坐标空间**：
- ArtMesh 顶点/UV：画布像素（Editor 打开后自动重烘焙为 warp-local 0..1）
- ArtMesh keyform 顶点：warp-local 0..1
- Rotation/Warp Deformer 的 origin/位移场：另一套空间（修复值 (43,-1033) 为画布外负坐标）

脚本修改只能在"猜测的坐标系"里打补丁。**同一份文件在 Editor 渲染、moc3 导出、SDK 运行时三条路径上表现不一致**，导致：修复无法可视化验证 → 每次迭代靠设备端观察 → 效率极低。我们已经用"Editor 打开另存 + 逐字节 diff"确认 Editor 未重烘焙数据，但**始终无法确定 Editor 期望的坐标约定**。

**期望指导**：
- Cubism Editor 工程格式（cmo3）中各类数据（ArtMesh 顶点、ArtMeshForm、CWarpDeformerForm、CRotationDeformerForm 的 origin）各自的确切坐标空间定义与变换链
- 是否有公开资料/工具/社区对 stretchystudio 导出的 cmo3 做"Editor 兼容化"处理
- 是否有办法禁用/绕过 Editor 的自动坐标处理，让脚本修改的数据原样渲染

### 困难 2：静态立绘 → 张嘴结构（无素材问题）

静态立绘没有张嘴素材（牙齿、口腔内部、舌头）。纯几何变形（唇线张开）在 15×5px 的小嘴上视觉不可感知。正在探索程序化生成口腔纹理 + 几何 keyform，但**缺少行业标准做法参照**。

**期望指导**：
- Live2D 批量/自动化项目中"嘴部结构"的行业做法（模板复用？程序化生成？）
- 是否有开源的标准嘴部素材库（可改色适配）

### 困难 3：300+ 角色规模化的质量控制

seethrough 分割质量随立绘风格波动（噪声像素是根因），需要自动质检环节（bbox 合理性、pivot 位置、部件方向一致性）。**期望指导**：批量 Live2D 项目的质检经验。

## 五、问题清单（浓缩版）

1. **坐标系**：cmo3 工程格式中 ArtMesh / ArtMeshForm / DeformerForm(origin) 的坐标空间定义是什么？如何让脚本生成的 cmo3 与 Editor 渲染一致？（当前最大障碍）
2. **自动绑骨**：社区是否有比 stretchystudio 更成熟的"PSD → cmo3"自动绑骨方案？网页版 stretchystudio 的算法能否通过其他途径获取/授权？
3. **嘴部自动化**：批量 Live2D 的嘴部（张嘴/口腔）自动化做法是什么？是否有开源素材或工具链？
4. **规模化质检**：批量自动生成的 Live2D 模型如何做自动质检（骨架/变形器质量判定）？
